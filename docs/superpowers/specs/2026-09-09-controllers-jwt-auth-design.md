# Дизайн HTTP-слоя и JWT-аутентификации — File Storage REST API

Дата: 2026-09-09
Статус: согласован с пользователем (брейнсторминг), готов к переходу в implementation plan

## Контекст

Сервисный слой (`User`/`File`/`Event` — CRUD, upload-flow, soft/hard delete) полностью готов и
закрыт, см. `docs/superpowers/specs/2026-09-08-service-layer-design.md` и `PROGRESS.md`. Это
следующий шаг — HTTP-слой поверх готовых сервисов.

**Изменение плана по ходу брейнсторминга**: изначально Security/JWT были сознательно отложены "на
самый конец", после HTTP-слоя. Пользователь пересмотрел это решение прямо в начале этого
брейнсторминга — сознательно, не из растерянности перед промежуточным вопросом (проверено явным
вопросом), с обоснованием "боюсь потом сам запутаться и агент запутается" (риск потери контекста
между сессиями при откладывании). Решено включить **аутентификацию** (JWT: логин/регистрация,
проверка токена, извлечение `userId`) в этот же брейншторм/спеку.

**Явно вынесено за рамки этого документа**: **ролевая авторизация** — фильтрация данных по роли
("USER видит только своё", `MODERATOR` может править чужое) — это отдельный, содержательно более
сложный вопрос (`@PreAuthorize`/`SecurityContext`-паттерны), идёт **отдельным** циклом
брейншторм → спека → план сразу следующим шагом, без большого разрыва по времени. В этом документе
роль **есть** в токене и в модели данных, но нигде не используется для ограничения доступа —
любой аутентифицированный юзер может дёргать любую ручку.

## Архитектура

- Новые пакеты: `controller` (HTTP-контроллеры), `security`/`auth` (JWT-механика: генерация,
  валидация, конфигурация Security-цепочки)
- Стиль контроллеров — аннотационный (`@RestController`, `@GetMapping`/`@PostMapping` и т.п.), не
  функциональный (`RouterFunction`) — оба варианта в WebFlux валидны, выбран привычный по
  предыдущим модулям. Методы возвращают `Mono`/`Flux`, как и весь остальной код проекта
- **Версионирование API — через `Accept`-заголовок** (media-type), не через URI. Отличие от
  модуля 2.4 (там был `/api/v1/...`) — сознательный пересмотр в эту сессию: 2.4 сделали
  URI-based ради простоты вопреки рекомендации собственного источника (habr-статья про REST,
  раздел 4); здесь решили попробовать вариант, который сам источник называл предпочтительным.
  Пути без версии в URI: `/users`, `/files`, `/events`, `/auth`
- `userId` в контроллере — из аутентифицированного `Authentication`/`SecurityContext`
  (`@AuthenticationPrincipal` или эквивалент), не из хедера — раз делаем JWT сразу, временный
  приём с `User-Id`-хедером (как в 2.4) не нужен вовсе

## Изменения в модели данных

`User` получает два новых поля, которых не было в исходном DDL ментора (DDL описывал сущности до
Security-этапа, расширение под него — ожидаемо, не нарушение, в отличие от предыдущих находок
вроде `TIMESTAMP`/`owner_id`, где менялось уже задействованное поле):

- **`password`** — String, хранит **хеш** (BCrypt), не сам пароль и не "зашифрованный" пароль
  (шифрование обратимо, хеширование — нет; для пароля нужно последнее)
- **`role`** — enum-подобная колонка (`VARCHAR`, как уже есть `status`), значения
  `ADMIN`/`MODERATOR`/`USER`. **Не отдельная таблица** — у юзера ровно одна роль (связь 1:1), а
  отдельные таблицы оправданы для "многие ко многим"

Новая миграция `V4__add_auth_fields_to_users.sql`:
```sql
ALTER TABLE users
    ADD COLUMN password VARCHAR(255) NOT NULL,
    ADD COLUMN role VARCHAR(50) NOT NULL DEFAULT 'USER';
```
(точный DEFAULT/nullable-статус для существующих строк — уточнить на этапе плана, если в БД уже
есть данные без пароля/роли на момент миграции)

`UserService.create(...)` — сигнатура меняется, принимает пароль (сырой, хешируется внутри
сервиса перед сохранением, через `PasswordEncoder`). **Роль не передаётся вызывающим** — жёстко
`USER` внутри сервиса, независимо от того, что прислал клиент (защита от эскалации привилегий при
самостоятельной регистрации).

`UserDto` — `password`/хеш **никогда** не попадает в API-ответы (по аналогии с тем, как `location`
не попадает в `FileDto`). Роль — не секрет, можно отдавать.

**Первый ADMIN-аккаунт** — заводится вручную (прямая SQL-вставка с уже готовым BCrypt-хешем), не
через API. Обычный `/auth/register` всегда создаёт `USER`; повышение до `ADMIN`/`MODERATOR` —
отдельный защищённый механизм, не спроектированный в этом документе (не нужен прямо сейчас,
единственный админ заводится вручную один раз).

## JWT-поток

**`POST /auth/register`** (открытый, без токена) — принимает `{username, password}`, создаёт
юзера с ролью `USER` (см. выше), возвращает `UserDto`. Открытость обоснована буквально
необходимостью: если бы регистрация требовала токен — получился бы замкнутый круг (нужен токен,
чтобы зарегистрироваться, но нужно зарегистрироваться, чтобы получить токен).

**`POST /auth/login`** (открытый, без токена) — принимает `{username, password}`, ищет юзера,
сверяет хеш пароля (`PasswordEncoder.matches(...)`, не "расшифровка"), при успехе — генерирует
JWT: кладёт в payload `userId` и `role`, время истечения (TTL — конкретное значение решить на
этапе плана), подписывает секретным ключом (библиотека `jjwt`, уже в зависимостях). Возвращает
токен.

**Оба этих пути объединены под общим `/auth/*`, вместе с любыми другими операциями, не требующими
токена** — сознательное решение вместо изначально предложенного `POST /users` для регистрации.
Причина: если открытая операция (`POST`) висит на том же пути, что и закрытые (`GET`/`PUT`/`DELETE`
на `/users`), легко ошибиться при настройке правил Security (одно неверное правило — либо весь
`/users` случайно откроется, либо регистрация случайно потребует токен). Собрав все "не требующие
токена" операции в одном месте (`/auth/*`), правило Security становится одним простым: "всё под
`/auth/` — без токена, всё остальное — только с валидным токеном". Проверено на реальном коде
BNPL (`AuthorizationController`, `@RequestMapping(RestPaths.AUTH_PATH)`, `/login` и `/register`
рядом в одном контроллере) — та же структура.

**Проверка токена на каждом остальном запросе** — стандартная реактивная Security-цепочка (по
образцу источника №8 из теории модуля): конвертер достаёт токен из заголовка `Authorization:
Bearer <token>`, `ReactiveAuthenticationManager` проверяет подпись и срок годности **без похода в
БД** (userId/role уже лежат готовые в payload токена — в этом весь смысл statelessness JWT).
Результат кладётся в реактивный `SecurityContext`, контроллер достаёт `userId`/`role` оттуда.

**Публичные пути (без токена)**: `/auth/register`, `/auth/login`, Swagger/OpenAPI-эндпоинты.
Всё остальное требует валидный токен.

**Отзыв токенов — сознательно не реализуется.** Обсуждали: если токен украден, сервер не может
отличить настоящего юзера от укравшего (пароль на обычных запросах не проверяется, только подпись
токена) — это архитектурное ограничение JWT (как и в реальном BNPL решается через Redis-blacklist).
Для этого проекта — принято как есть, единственная защита — короткий TTL токена. Redis не
добавляется.

## Контроллеры и роуты

**`AuthController`**
- `POST /auth/register` — регистрация, открытый
- `POST /auth/login` — логин, открытый

**`UserController`** (весь целиком требует токен, без исключений)
- `GET /users/{id}`, `GET /users`
- `PUT /users/{id}` (rename)
- `DELETE /users/{id}`

**`FileController`** (весь целиком требует токен)
- `POST /files` — multipart upload; `FilePart` собирается в `byte[]` (честный стриминг на upload
  сознательно не делается — см. `PROGRESS.md`, ограничение S3-протокола на content-length);
  `userId` — из токена, не из тела запроса
- `GET /files/{id}` — метаданные (JSON, без `location`)
- `GET /files/{id}/download` — отдельный путь под бинарное содержимое, стримит `Flux<byte[]>` как
  тело ответа. Разделение на два пути — потому что один HTTP-ответ не может одновременно быть и
  JSON-объектом, и потоком сырых байт; нужно два разных пути под два разных вида ответа,
  соответствующих двум уже существующим методам сервиса (`getById`/`getContent`)
- `GET /files` — список
- `DELETE /files/{id}` — архивация

**`EventController`** (весь целиком требует токен)
- `GET /events/{id}`, `GET /events`
- `DELETE /events/{id}`

Ролевые ограничения (кому какие ручки реально доступны по ТЗ) — не в этом документе, см. секцию
"Вне рамок" выше.

## Валидация входных данных

Через аннотации (`@Valid` + `jakarta.validation` на request-DTO), а не ручные проверки в коде —
`spring-boot-starter-validation` уже в зависимостях проекта.

## Обработка ошибок

Единый `@RestControllerAdvice` (не размазанный по контроллерам), маппинг:

| Исключение | HTTP-код |
|---|---|
| `NotFoundException` (уже есть в сервисном слое) | 404 |
| Ошибка `@Valid`-валидации | 400 |
| Неверный логин/пароль на `/auth/login` | 401 |
| Токен невалиден/просрочен (падает на уровне Security-фильтра, до контроллера) | 401 |
| `FileStorageUnavailableException` | 503 |
| `DataIntegrityViolationException` (FK/constraint) | 409 или 422 — точный код решить на этапе плана |

Единообразный JSON-ответ вида `{"error": "...", "status": ...}`, по аналогии с
`ExceptionHandlingFilter` из модуля 2.4.

## Вне рамок этого документа

- Ролевая авторизация/фильтрация данных — отдельный следующий цикл брейншторм → спека → план
- Отзыв токенов (Redis-blacklist и подобное) — сознательно не делается
- Повышение юзера до `ADMIN`/`MODERATOR` через API — не спроектировано, первый админ заводится
  вручную
- Честный потоковый upload (`put()` в MinIO) — уже решённый в сервисном слое компромисс, не
  пересматривается здесь
