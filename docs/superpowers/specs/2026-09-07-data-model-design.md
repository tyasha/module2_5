# Дизайн модели данных — File Storage REST API

Дата: 2026-09-07
Статус: согласован с пользователем (брейнсторминг), готов к переходу в implementation plan

## Контекст

Практика модуля 2.5 — REST API для файлового хранилища на MinIO S3, с JWT-авторизацией и
разграничением прав (ADMIN/MODERATOR/USER). Стек: Spring Boot 4.1.1, WebFlux, Spring Data R2DBC
(не JPA — см. `PROGRESS.md` → «Архитектурное решение №1»), MySQL, Flyway, Gradle.

Сущности и DDL заданы ментором (см. `PROGRESS.md` → «Задача от ментора»). Этот документ фиксирует
решения по тому, как именно эта модель ляжет в код: миграции, поток загрузки файла, доступ по
ролям, структура пакетов.

## Сущности

Строго по DDL ментора, без дополнительных полей (обсуждали и сознательно отклонили аудит-поля
`created_at`/`updated_at` на `User`/`File` — они не несут функциональной нагрузки при выбранном
дизайне upload-flow, см. ниже).

- `User` — id (Integer), username (String), status (enum: ACTIVE, BLOCKED)
- `File` — id (Integer), name (String), location (String — MinIO URL), status (enum: ACTIVE, ARCHIVED)
- `Event` — id (Integer), user_id (Integer, FK), file_id (Integer, FK), status (enum: CREATED,
  UPDATED, DELETED), timestamp (LocalDateTime)

Прямой связи `files → users` нет — владелец файла определяется через `Event` (см. ниже).

## Миграции (Flyway)

Один файл на таблицу, в порядке FK-зависимости:
- `V1__create_users.sql`
- `V2__create_files.sql`
- `V3__create_events.sql` (FK на users и files)

FK-constraints — на дефолтном движке хранения MySQL (InnoDB), `ENGINE=` явно не указываем, как и
в DDL ментора. (Разобрано: MyISAM тихо не создал бы реальный constraint при синтаксически
валидном `REFERENCES` — но это не наш случай на дефолтной конфигурации MySQL 2026.)

## Upload-flow и согласованность MinIO/БД

Порядок: **сначала запись в MinIO, затем создание `File`+`Event` в БД** (одной DB-транзакцией).
MinIO и БД — независимые системы, распределённой транзакции между ними нет.

Разобрали риск: если DB-часть упадёт (или процесс погибнет) уже после успешной записи в MinIO —
останется файл-сирота в MinIO без записи в БД. Более полное решение (промежуточный статус
`PENDING` на `File`, `created_at`, фоновый шедулер-реконсилятор) обсуждали, но **отклонили** —
сверились с реальным продакшен-кодом BNPL (`be-files/service/impl/FileService.java`): там тот же
порядок (MinIO → БД) и никакой реконсиляции нет вообще, риск принят как есть. Решили сделать так
же, не добавлять сложность сверх того, что оправдано на этом масштабе.

## Владелец файла

Прямой колонки-владельца на `files` нет. Владелец определяется через `events`:

```sql
SELECT u.* FROM users u
JOIN events e ON e.user_id = u.id
WHERE e.file_id = :fileId AND e.status = 'CREATED'
```

Фильтр именно по `status = 'CREATED'`, а не "самый ранний по timestamp" — явное выражение
бизнес-правила, не полагание на побочный эффект сортировки по времени.

## Доступ к содержимому файла

`GET /files/{id}` стримит байты файла напрямую через бэкенд (бэкенд ходит в MinIO своими
внутренними кредами и проксирует контент клиенту). Поле `location` (внутренний MinIO-путь)
**нигде не отдаётся клиенту** ни в одном API-ответе, ни для одной роли — только используется
внутри сервисного слоя.

Как следствие — presigned URL для доступа к файлу не нужен, разница между ролями по `File` на
уровне ПОЛЕЙ отсутствует.

## DTO и разграничение по ролям

**Один DTO-класс на сущность**, не по ролям. ТЗ ментора описывает разграничение доступа целиком
на уровне СТРОК и ОПЕРАЦИЙ ("все User", "свои данные"), не полей внутри записи — значит,
разграничение реализуется на уровне сервис/репозиторий-слоя (какие записи вообще попадают в
выборку для данной роли), а не через разные формы одного и того же объекта.

| Роль | User | Event | File |
|---|---|---|---|
| ADMIN | всё | всё | всё, любые операции |
| MODERATOR | чтение всех | чтение/изменение/удаление всех (+ права USER) | чтение/изменение/удаление всех (+ права USER) |
| USER | чтение своей записи | чтение своих (через `events.user_id`) | чтение своих (через `events`, см. выше) + загрузка за себя |

## MinIO-клиент

`S3AsyncClient` (Netty, неблокирующий), не `S3Client` — согласовано с реактивным стеком.
`apache5-client` (синхронный, тащится транзитивно вместе с `s3`-модулем AWS SDK) явно исключён
из `build.gradle`, чтобы не было соблазна случайно взять блокирующий клиент.

## Технические следствия (R2DBC, из архитектурного решения №1)

- `Repository` — не `JpaRepository`, а `ReactiveCrudRepository`/`R2dbcRepository`, методы
  возвращают `Mono`/`Flux`
- Entity-классы (`model`) — аннотации Spring Data R2DBC (`@Table`, `@Column`), не JPA
  (`@Entity`/`@ManyToOne` и т.п. недоступны/не нужны — связи моделируются через прямые FK-поля
  (`Integer userId`, `Integer fileId`), не через объектные ссылки)
