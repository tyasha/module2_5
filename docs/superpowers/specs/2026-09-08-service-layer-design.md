# Дизайн сервисного слоя — File Storage REST API

Дата: 2026-09-08
Статус: согласован с пользователем (брейнсторминг), готов к переходу в implementation plan

**Поправка по факту реализации (не переписываю оригинальные строки ниже, чтобы не терять честную
историю "что предполагали / что оказалось на деле"):** координаты Testcontainers-модуля для MinIO
и пакет класса ниже по тексту (`org.testcontainers:minio`, `MinIOContainer` без указания пакета) —
были правильной идеей, но неточным предположением. Проверено при реализации: зависимость —
`org.testcontainers:testcontainers-minio` (без явной версии, той же BOM, что и остальные
testcontainers-модули), класс — `org.testcontainers.containers.MinIOContainer` (не
`org.testcontainers.minio.MinIOContainer` — модуль MinIO, в отличие от MySQL, не мигрировал на
новую раскладку пакетов в Testcontainers 2.x).

## Контекст

Модель данных (Entity/миграции/DTO/мапперы) готова — см.
`docs/superpowers/specs/2026-09-07-data-model-design.md`. Этот документ — следующий слой:
конфигурация MinIO-клиента, upload-flow, CRUD-сервисы для `User`/`File`/`Event`.

**Security/JWT сознательно исключены из этого документа** — пользователь решил отложить их на
самый конец, после того как всё остальное заработает. Вся ролевая фильтрация доступа
("USER видит только своё") — тоже отложена целиком до этапа Security, см. ниже.

## MinIO — конфигурация и клиент

- **Бакет считается уже существующим** (поднят заранее, например через docker-compose) —
  приложение НЕ создаёт бакет программно при старте. Если бакета нет — операция с MinIO падает
  явно (fail fast), а не создаёт его тихо
- Клиент — `S3AsyncClient` (AWS SDK v2, асинхронный/неблокирующий — архитектурное решение №1,
  см. `build.gradle`, `apache5-client` исключён явно)
- Конфиг — по аналогии с `spring.r2dbc.*`/`spring.flyway.*` в `application.yml`: свои properties
  под MinIO (endpoint, access key, secret key, имя бакета)

## Именование объектов в MinIO

- **Ключ объекта — `UUID.randomUUID()`**, не оригинальное имя файла. Оригинальное имя (`name` в
  DDL) может совпадать у разных пользователей/загрузок — коллизия молча перезаписала бы чужой
  файл. UUID гарантирует уникальность
- **Поле `File.location` хранит только этот ключ** (не полный URL). Бакет — один и тот же на всё
  приложение, задан конфигом один раз — хранить его в каждой строке было бы дублированием одного
  и того же значения. Чтобы скачать файл, сервис комбинирует: бакет (из конфига) + ключ (из
  `location`)
- `location`, как и раньше, никогда не попадает в API-ответы ни для одной роли (решено в
  предыдущей спеке)

## Upload-flow (напоминание из предыдущей спеки, без изменений)

Порядок: сначала запись байтов в MinIO (по сгенерированному UUID-ключу), затем одной
DB-транзакцией — `File` (со `status = ACTIVE`, `location` = тот же UUID) и `Event`
(`status = CREATED`, `user_id` = загрузивший). Риск файла-сироты в MinIO при падении
DB-транзакции — принят осознанно (см. предыдущую спеку, сверка с реальным кодом BNPL).

## Идентификация текущего пользователя (без Security)

Пока нет JWT, методам сервисного слоя, которым нужно знать "кто выполняет действие"
(`FileService.upload`), **`userId` передаётся явным параметром**. Это не решение про
авторизацию — это просто данные (кто загрузил файл, чтобы создать `Event`), безразличные к
источнику: сегодня это может прийти из заголовка (как в модуле 2.4, `User-Id`), позже — из JWT.
Сигнатура сервисного метода не изменится при переходе на Security — изменится только то, что
именно подставляет в этот параметр будущий контроллер.

**Рассмотрели и отклонили на этом этапе**: retriever-паттерн (как `IUserIdRetriever` в
BNPL — интерфейс, инжектируемый в сервис, вместо явной передачи параметром). Оправдан, когда
"текущий пользователь" нужен в МНОГИХ местах вглубь по цепочке вызовов — сейчас нужен только в
одном месте (`upload`), заводить абстракцию под это — YAGNI. Если появится больше таких мест —
вернуться к этому паттерну.

## Ролевая фильтрация доступа — вне рамок этого документа

`GET`-методы сервисов (`getById`/`getAll` для `User`/`File`/`Event`) реализуются как **простые
CRUD-операции без фильтрации по ролям** — отдают то, что просят, без проверки "своё это или
чужое". Разграничение доступа по ролям ("USER видит только своё") целиком стоит на связке
userId+role, которая содержательно ЯВЛЯЕТСЯ авторизацией — реализовывать её до появления
настоящего Security означало бы строить временную конструкцию, которую придётся переделывать под
идиомы Spring Security (`@PreAuthorize`, `SecurityContext`) при переходе на JWT. Осознанно
отложено целиком на этап Security, одним куском, а не размазано по двум сессиям работы.

## Удаление — soft delete vs hard delete

- **`User`** — soft delete: `status → BLOCKED`, строка не удаляется физически
- **`File`** — soft delete: `status → ARCHIVED`, строка не удаляется физически
- **`Event`** — **honest hard delete** (реальное удаление строки), несмотря на то что `Event` по
  смыслу — аудит-лог. В ТЗ явно разрешено MODERATOR удалять любые Event; обоснованный жизненный
  сценарий — очистка старых событий по политике ретеншена (модератор чистит аудит за прошлый
  год), а не архитектурный недосмотр. У `Event` в принципе нет свободного поля под soft delete
  (`status` занят описанием, ЧТО произошло с файлом, не состоянием самой записи события)

## Обработка ошибок MinIO

Исключения от `S3AsyncClient` оборачиваются в собственный тип исключения (например,
`FileStorageUnavailableException`, unchecked — совместимо с реактивными сигнатурами), а не
пробрасываются как есть. Цель — чтобы вызывающему коду (в перспективе — контроллеру и его
error-хендлеру) было явно понятно "внешнее хранилище недоступно/легло", а не разбираться в
деталях конкретного SDK-исключения.

## Тестирование — MinIO через Testcontainers

Тот же паттерн "singleton containers", что уже используется для MySQL в
`AbstractIntegrationTest` (без `@Testcontainers`/`@Container`, ручной `static`-блок с `.start()`)
— модуль `org.testcontainers:minio`, класс `MinIOContainer`. Через `@DynamicPropertySource`
адрес и креды контейнера подставляются в конфиг MinIO-клиента вместо продовых значений — тесты
гоняют реальный MinIO в Docker, не мок. Точные координаты зависимости и пакет класса — уточнить
при реализации (проверено на момент брейнсторминга: `org.testcontainers:minio:2.0.1`,
`MinIOContainer`, но версия могла обновиться к моменту реализации).

## Возврат данных из сервисов

Сервисные методы возвращают DTO (`UserDto`/`FileDto`/`EventDto`), не entity — используют уже
готовые мапперы (MapStruct) внутри. Пакеты — `service`/`service/impl`, по аналогии со стилем 2.4
(интерфейс + реализация раздельно).

## Вне рамок этого документа

Security/JWT, ролевая фильтрация доступа (см. выше — целиком уезжает на этап Security),
REST-контроллеры и их сигнатуры, `GET /files/{id}` как стриминг-эндпоинт (упомянут в предыдущей
спеке как решение "location не светится", но сам HTTP-слой — отдельный, ещё не обсуждённый шаг).
